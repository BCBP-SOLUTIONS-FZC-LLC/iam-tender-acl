## New work — nothing to copy, because it doesn't exist anywhere yet

Three things below were **not found anywhere in the codebase** during research for this task. Do not treat their absence as "must have been missed" — verify independently, then build them as new code, flagging each explicitly in the deliverable docs (below) rather than silently inventing a design.

1. **The `membershipcheck` client** (LLD §6, §7.6.2). Build `internal/membershipcheck/` in the new repo: a small interface (`Exists(ctx, tenantID, userID) (bool, error)`) plus an HTTP adapter calling `GET /internal/tenants/:id/members/:user_id/exists` on `iam-org-membership`, ≤50ms client-side budget, `503 core_unavailable` on failure — mirroring the thin, fail-open-aware outbound-client pattern `iam-catalog-admin`'s `O_AND_M_DELTA.md` §4 describes for its own new client, adapted to fail **closed** here (grant blocked, not defaulted) per LLD §7.6.2/TAC-FAIL-1.

2. **A new provider endpoint in `iam-org-membership`.** `GET /internal/tenants/:id/members/:user_id/exists` does not exist today — confirmed by reading `internal_handler.go` in full. It needs to wrap `MembershipRepository.FindByUserID` (in `internal/core/port/membership_repository.go`) and return `{"active": true}` when found with `Status == domain.MembershipActive`, `{"active": false}` on `ErrMemberNotFound` or any non-active status. **This is server-side work belonging to `iam-org-membership`, so it goes in `O_AND_M_DELTA.md` as a new-endpoint spec, not in this task's own code** — unlike the catalog-admin extraction, where `iam-org-membership` was purely the *consumer* of a new endpoint, here it must become the *provider* of one. Say this explicitly in the delta doc so the follow-up task doesn't miss that the data-flow direction is reversed from precedent.

3. **The per-user-removal ACL cascade gap.** `MembershipService.RemoveUser` (P-8/I-5, `internal/core/service/membership_service.go`, around line 544) currently does a **synchronous, same-transaction** `s.acls.SoftDeleteForUser(txCtx, tenantID, userID)` — soft-deleting the removed user's `tender_acl_entries` rows inside the *same* database transaction as the membership removal, with **no event emitted for it** (unlike the role/dept/delegation cascades three steps earlier in the same method, which each emit `TenantRoleRevoked`/`DepartmentMembershipRevoked`/`DelegationEnded`). The LLD's §10.1 only documents the **tenant-offboarding** cascade — this **per-user-removal** cascade was never accounted for anywhere in the LLD, and once the table lives in a separate database this same-transaction call becomes physically impossible. This is a real design gap, not a documentation nit. Recommend, but do not silently decide: reuse the existing "post-commit best-effort, fire-and-forget" pattern `RemoveUser` already applies two lines later for Realm Provisioner's `RevokeUserSessions` (line ~561) — i.e. `iam-org-membership` calls a new `internal/adapter/outbound/tenderacl/` client's `NotifyUserRemoved(ctx, tenantID, userID)` after commit, best-effort, non-blocking — rather than inventing a new SNS event for what is otherwise a low-stakes, inert-if-delayed cascade (consistent with the LLD's own TAC-EVT-4/TAC-FAIL framing that a delayed cascade here is never a live authorization risk, since a removed user can't present valid headers again regardless). Write this recommendation and the alternative (a new lightweight event) into both `O_AND_M_DELTA.md` and `IMPLEMENTATION_GAP_ANALYSIS.md`, and flag it for explicit review before a follow-up task implements either side.

## Discrepancy to reconcile, not silently paper over

The LLD's §12.1/§12.5 (failure matrix row "Optimistic-lock conflict on TAC-3 revoke") describes a client-supplied `record_version` check on revoke returning `409 optimistic_lock_conflict`. **The actual `Revoke()` method in `tender_acl_repository.go` takes no version parameter and performs no such check** — it is a plain `UPDATE ... WHERE ... AND deleted_at IS NULL`. Per ADR-0007's "preserve every... behaviour... unchanged" instruction (LLD §2), **implement `Revoke` exactly as it exists today — no optimistic-lock check** — and record the LLD/code mismatch in `IMPLEMENTATION_GAP_ANALYSIS.md` rather than adding new caller-visible behavior nobody currently sends a `record_version` for. If you believe the optimistic-lock check should genuinely be added, say so in that doc as a recommendation, but do not add it unannounced in this pass.
